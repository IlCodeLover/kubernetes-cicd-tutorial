# Kubernetes CICD Tutorial

This repo contains all the code needed to follow along with our **[YouTube Tutorial](https://youtu.be/GlhK7mz5IJo)** or **[Written Article](https://rslim087a.github.io/rayanslim/lesson.html?course=kubernetes-cicd-course&lesson=introduction)**.

- CI part - Repo kubernetes-cicd-tutorial: contain source code in node for CRUD grade via Rest API + GitHub Actions workflow (CI)
  - whenever a changes in git, that will trigger auto build image and push to GHCR, then update the deployment.yaml in gitops repo to link to that new image tag/sha
  
- CD part - Repo grade-api-gitops (CD part): contain Kubernetes manifests for deployment and tracked by Argo CD (CD)
  - deployment.yaml: Deployment manifest for the app, with image: field set to a placeholder tag. The GitHub Actions workflow will update this field to the new image tag after building and pushing the image.
  - existing image in deployment.yaml: ghcr.io/ilcodelover/kubernetes-cicd-tutorial:latest will be updated to link to new image with hash number "ghcr.io/ilcodelover/kubernetes-cicd-tutorial:e769fac4ef255b74d42fe6e60c3331c65fa99cee"
  
  > sed -i '' "s|image: ghcr.io/${LOWER_REPO}:.*|image: ghcr.io/${LOWER_REPO}:${{ github.sha }}|g" deployment.yaml
  - GitOps triggers the CD part of our pipeline.
  - ArgoCD watches the GitOps repo and when it sees new image tag/sha, it will redeploy k8s manifest (new image) inside the k8s cluster automatically to reconcile the actual state in K8s cluster with the desired state in GitOps repo. 
- Local folder "actions-runner": contain self-hosted runner for GitHub Actions workflow that are generated by GitHub when you create a new self-hosted runner on your repo.

## Automation CICD

- Push code → Github Action (CI workflow triggers, e.g file ci-cd.yml) →  Build Image → Push to GHCR (image stored in GHCR) → Update GitOps repo to point to new image tag/sha → ArgoCD watches the GitOps repo and when it sees new image → Auto Deploy (End-to-End)

- Changes to the app repo trigger a GitHub Actions workflow that builds a Docker image and pushes artifacts (images) to a container registry GHCR. The workflow then updates the GitOps repo to reference the new image tag/sha. Argo CD detects the change and reconciles the cluster automatically.

## Separation of Concerns (CI vs. CD):

- CI (Application repo): Build & push image, then programmatically update the GitOps manifest.
- CD (GitOps repo): Argo CD watches the repo and applies drift correction to the cluster.

**GitHub Actions Essentials**: Use built-in actions to check out code, authenticate to GHCR, build & push, then a script step to edit the Deployment’s image: field to the new digest. Store credentials as repository secrets (e.g., a registry PAT and a GitOps-repo PAT).

**Self-Hosted Runner & Docker**: The example uses a self-hosted runner (Docker required) to execute the workflow locally. Ensure Docker is running so the buildx and push steps succeed.

**Argo CD Setup & Sync**: Install Argo CD via Helm/manifests, port-forward the argocd-server, and create an Application pointing at the GitOps repo/path. Enable options like auto-sync/prune/self-heal as desired for hands-off deployments.

**Observe the Full Flow**: Make a tiny code change → workflow builds & pushes → GitOps repo gets updated → Argo CD syncs → new Pods run the latest image. You’ve got a professional GitOps-style CI/CD from commit to cluster.

### Configure github personal access token    
- Open Github, Profile -> Setting -> Developer setting -> Personal access tokens -> Create new CR_PAT (for having permission to package things up into image and push image to GHCR) and GITOPS_PAT (for updating template deployment.yaml in gitops)
  - CR_PAT: in the scopes, select repo (all suboptions); workflow option; write packages.
  - GITOPS_PAT: in the scopes, select repo (all suboptions) only because it is sufficient to update the deployment.yaml in gitops repo. No need to select workflow option and write packages.
- Save the key in your text IDE immediately.
- Go to repo kubernetes-cicd-tutorial -> Setting -> Secrete and Variables -> Action -> click New Repository secret -> Add 2 tokens with exact names (CR_PAT, GITOPS_PAT) as you created them previously so that this repo can have proper access when CI.
- file ci-cd.yml should be updated to use credentials and git repo name correctly.

```bash
  # this job has many steps and some of them are using github actions to perform tasks like checking out code, logging into GHCR, building and pushing docker images, and updating the GitOps repository.
  build-and-push:
    # this pipeline will be run on your host machine, not on Github server. So, you need to config self-hosted runner on your local machine first.
```

### Install ArgoCD
- GitOps repo contains Kubernetes manifests for deployment and tracked by Argo CD (CD). Argo CD watches the GitOps repo and when it sees new image tag/sha, it will redeploy k8s manifest (new image) inside the k8s cluster automatically to reconcile the actual state in K8s cluster with the desired state in GitOps repo.
- K8s cluster: resources are created and managed by Kubernetes. The cluster can be on your local machine (Docker Desktop) or in the cloud (AWS, GCP, Azure, etc.). For this tutorial, we will use Docker Desktop with Kubernetes enabled. (Run Docker --> Setting -> Kubernetes --> Enable Kubernetes)

- Install ArgoCD on local Kubernetes cluster (Docker Desktop) via Helm 
```bash

# Keeping Argo CD in its own namespace separates the control plane tools from your actual running applications (like your grade-submission-api).
kubectl create namespace argocd
```

## Create ArgoCD Application
- Copy this content and save into file argocd-application.yaml in any folder, e.g: 
    \devops
        |__actions-runner\
        |__kubernetes-cicd-tutorial\
        |__argocd-tutorial\
           |__argocd-application.yaml
```yaml
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: grade-submission-api
  namespace: argocd
spec:
  project: default
  source:
    repoURL: https://github.com/YOUR_USERNAME/grade-api-gitops.git
    targetRevision: HEAD
    path: .
  destination:
    server: https://kubernetes.default.svc
    namespace: default
  syncPolicy:
    automated:
      prune: true
      selfHeal: true
```

- update git repo to yours
- Run
```bash

cd argocd-tutorial

```

## Troubleshooting
###  kubectl create namespace argocd --> got error "The connection to the server localhost:8080 was refused - did you specify the right host or port?"
- Root cause: kubectl has no Kubernetes cluster to talk to. You don't have a ~/.kube/config file and no contexts are set, so kubectl falls back to localhost:8080, where
nothing is running.
- Solution: create a cluster.
```bash
1. Open Docker Desktop → Settings  → Kubernetes.
2. Tick Enable Kubernetes, then click Apply & Restart. Setup takes a few minutes and is done when the Kubernetes icon at the bottom turns green.
3. This creates ~/.kube/config with a docker-desktop context. Check it with:
   
   kubectl get nodes        # should show: docker-desktop   Ready
   kubectl create namespace argocd
   kubectl get namespace # should show your namespace
```
### dial unix backend.sock: connect: connection refused

The message Post "http://ipc/registry/credstore-updated": dial unix backend.sock: connect: connection refused means that the Docker CLI on your self-hosted runner machine is trying to use an external credential store (like Docker Desktop or a specialized credential helper) that expects a background socket (backend.sock) to be running.
Config docker so that self-host runner can access docker
```
(base) ➜  ~ cat ~/.docker/config.json
{
"auths": {
"https://index.docker.io/v1/": {}
},
"_disabled_credsStore": "desktop" // old value: "credsStore": "desktop"
}

```

### Why deleting docker containers of k8s- doesn't work:
-  Kubernetes keeps the cluster matching what's declared. Your Deployment says replicas: 1, so when
   a container disappears, Kubernetes starts a new one. The _4 at the end of your app's container name is a restart count, which
   suggests it has been recreated several times after your deletes. The ArgoCD and system pods are recreated the same way.

1. Pause ArgoCD but keep it installed (scale to 0):
   kubectl -n argocd scale deploy --all --replicas=0
   kubectl -n argocd scale statefulset --all --replicas=0
   To bring it back later, run the same commands with --replicas=1.

2. Remove ArgoCD completely:
   kubectl delete namespace argocd
   This removes all of ArgoCD's pods, Deployments, config and secrets. To use it again, you'd have to reinstall it and recreate the
   Application.

3. Stop Kubernetes entirely (this also stops the kube-system containers):
   Open Docker Desktop → Settings → Kubernetes, uncheck Enable Kubernetes, then click Apply & Restart. Ticking it again brings the
   cluster back. Docker Desktop also has a Reset Kubernetes Cluster button there, which wipes the cluster.

If you just want the Docker containers gone and you'll come back to the tutorial later, option 3 is the cleanest. Don't delete
kube-system pods or containers by hand, because they'll always be recreated.
